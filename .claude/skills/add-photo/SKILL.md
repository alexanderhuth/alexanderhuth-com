# Add Photo

Publishing a photo takes two things: the image at five sizes under `images/`, and a Markdown file in `_photos/`. The sizes are generated by a script; the Markdown file needs details only the user has.

## When To Use It

- The user dropped a photo into `images/` and wants it published.
- The user wants to write or review the front matter for a photo entry.
- The user needs a reminder of the image size requirements.

## Workflow

**1. Generate the variants.**

The user drops the photo into `images/` under its intended filename. That filename is the slug — use it verbatim, do not rewrite or kebab-case it.

```bash
scripts/photo-sizes.sh images/<filename>.jpg
```

The script writes all five sizes, overwrites `images/<filename>.jpg` with the 1920px version, and prints ready-made `date`, `time`, `image`, `width`, and `height` values for the front matter. Take them from its output rather than measuring separately.

If the source's long edge is under 1920px the script says so and skips the steps it cannot fill without upscaling. Tell the user which steps are missing — the photo still renders, but at lower resolution on large screens.

**2. Look at the photo, then ask for the details the script cannot know.**

Open `images/<filename>.jpg` with the Read tool first. Never write alt text from the filename alone — the filename is a slug, not a description.

From what you see, draft:

- `alt` — what the photo shows, written for someone who cannot see it. Describe the subject, setting, and anything that carries the meaning of the shot. Skip "photo of" and "image of". One or two sentences.
- `title` — short and descriptive, a suggestion only.
- `location` — only if the image makes it unambiguous (a recognisable landmark, a legible sign). Never guess from the filename or from a general resemblance.

Then ask for everything in one go, presenting the drafts for approval rather than as open questions:

- `alt` — show the drafted text and ask the user to approve or amend it
- `title` — show the suggestion and ask the user to approve or amend it
- `date` / `time` — if the script printed them, show them for confirmation rather than asking outright. If it reported no EXIF timestamp, ask for the date and time the photo was taken.
- `location` — show the suggestion if you have a confident one, otherwise ask
- `camera` — optional, ask

Use the AskUserQuestion tool when it fits, with your draft as the first option, so approving is one click and amending is still open. Take the user's wording over your own whenever they amend.

**3. Create `_photos/<slug>.md`** with the front matter below, using the values the user confirmed and the `width`/`height` from the script's output.

**4. Build and report.**

```bash
bundle exec jekyll build --quiet
```

Then report the URL (`/photos/<slug>/`), the generated sizes, and anything still missing.

## Front Matter

Front matter only — the file has no body content.

```yaml
---
layout: photo
title: "Photo Title"
robots: noindex
date: YYYY-MM-DD HH:MM:00 +02:00
time: "HH:MM"
image: /images/slug.jpg
width: 1440
height: 1920
alt: "Descriptive alt text for the photo."
location: "Location name"
---
```

| Field | Required | Notes |
|---|---|---|
| `layout` | yes | Always `photo` |
| `title` | yes | Short, descriptive title |
| `robots` | yes | Always `noindex` |
| `date` | yes | Full datetime with timezone: `YYYY-MM-DD HH:MM:00 +02:00` (`+01:00` in winter / CET, `+02:00` in summer / CEST). Taken from the script's EXIF output where available, rounded up to the next five minutes. The feed sorts by `date` descending, so the time component must be correct. |
| `time` | yes | `"HH:MM"` — shown on the detail page and in the feed caption |
| `image` | yes | `/images/<slug>.jpg` — from the script output |
| `width` | yes | Width of the 1920px file — from the script output |
| `height` | yes | Height of the 1920px file — from the script output |
| `alt` | yes | Descriptive alt text; also used in the Atom feed |
| `location` | no | Where the photo was taken |
| `camera` | no | Shown on the detail page |

`width` and `height` must match the actual `images/<slug>.jpg` file. The templates compute every `srcset` descriptor from them, so wrong values make browsers pick the wrong file. The script's output is authoritative.

## Image Sizes

Variants bound the **long edge**, so a portrait photo is narrower than its step name — a 1440×1920 photo yields a 360px-wide file at the 480 step. That is expected; `_includes/photo-figure.html` and `_includes/photos-grid.html` derive the real width from `width`/`height` and emit honest descriptors.

| Step | Directory | Used for |
|---|---|---|
| 1920px | `/images/` | Detail page |
| 1280px | `/images/1280/` | Feed (largest srcset step) |
| 960px | `/images/960/` | Feed srcset |
| 720px | `/images/720/` | Feed srcset + Atom feed embed |
| 480px | `/images/480/` | Feed srcset + grid |

Every variant is stripped of EXIF, encoded progressively, and 4:2:0 chroma subsampled. Quality rises with size: 82, 84, 86, 88, 92.

The script reads `DateTimeOriginal` from the source before stripping it and prints a ready-made `date` and `time`, rounded up to the next five minutes. The UTC offset is the one in effect locally on that date, so a photo taken in another timezone needs its offset corrected by hand.

## Response Pattern

After creating the file, report:

1. The filename created and its URL path (`/photos/<slug>/`).
2. The generated sizes, and any that were skipped because the source was too small.
3. Any field left as a placeholder that still needs the user's input.
